# The Vaults — store setup

The Vaults is a static storefront: every page under `vaults/` is generated by
`tools/store_build.py` from `data/products.json`. There is no server, no
database and no payment processing built into this site — checkout is
handled entirely by a third-party payment provider you choose at launch.
Until then the store runs in **preview mode**: visitors can browse, search
and add things to a basket, but checkout is not live.

## How it works today (preview)

- `data/products.json` → `config.checkout.provider` is `"none"`.
- Every store page shows a slim strip: *"PREVIEW · The Vaults open soon.
  Browse now, buy at launch."*
- Add to cart works (basket lives in the visitor's browser, `localStorage`).
- The basket's checkout button reads *"Checkout opens with the Vaults"* and
  reveals a waitlist form instead of taking payment.
- Product "Buy now" buttons add the item to the basket and go to the basket
  page, same as "Add to cart".
- Coupons and bundle savings are calculated and shown, but nothing is
  actually charged.

## Going live: pick a payment provider

You need a provider that can host a checkout page or link, take the money,
and email the customer their file. Two good fits for a small one-person
digital-goods store:

1. **Payhip** (recommended to start) — free plan, has a proper cart
   (multiple items in one checkout), coupon codes, digital delivery with
   permanent re-download links, and a customer portal. This matches how
   the Vaults basket already behaves (one checkout for many items).
2. **Shopify Starter** — heavier, but solid if you want a fuller commerce
   platform later (inventory, more products, upsells built in).

**Stripe Payment Links** are a fine backup for individual products but each
link checks out **one item only** — there is no multi-item Stripe Payment
Link. If you use Stripe, the site already accounts for this: see "Cart with
more than one item" below.

Whichever you pick, do this once per product/bundle:

1. Create the product in the provider (title, price, upload the PDF/ePub
   files as the digital delivery attachment).
2. Set the provider's **success/thank-you URL** to
   `https://ravolution.agency/vaults/thanks/`.
3. Copy the checkout link (Payhip "buy button" link, Shopify checkout link,
   or Stripe Payment Link URL).

## Wiring it into the site

Edit `data/products.json`:

```json
"config": {
  "status": "live",
  "checkout": {
    "provider": "links",
    "success_url": "/vaults/thanks/",
    "customer_portal_url": "https://payhip.com/dashboard/..."   // if the provider has one
  }
}
```

Then for **every** product and bundle you have made checkout-ready:

```json
"checkout": { "url": "https://payhip.com/b/xxxxx" }
```

Leave `"url": ""` for anything not ready yet — its buy button still works
(it will just fall back to the basket/waitlist flow) rather than breaking.

Also flip `"status": "live"` at the top level once you're ready to drop the
preview strip and swap the door's HUD line from "SCROLL TO PREVIEW ↓" to
"SCROLL TO ENTER ↓" (and its sub-line stops saying "opening soon.").

Then rebuild and deploy:

```
python3 tools/build.py --store --only vaults
```

(A full site deploy is just "push the built files" — nothing to run on a
server.)

## What happens client-side vs at the provider

| Feature | Handled by the site (client-side, for display) | Handled by the provider (actually charges/enforces) |
|---|---|---|
| Coupon codes (`coupons` in products.json) | Shows the discount and new total in the basket | You must **also** create the same code in your provider, or the discount shown on-site won't actually apply at checkout. Keep codes/percentages in sync by hand. |
| Bundle pricing (`bundles` in products.json) | Shows the bundle price/saving as its own product | Create the bundle as its **own product** in the provider (its own checkout link), priced the same — don't rely on the provider to total up three separate line items at the bundle price. |
| Upsell ("Complete the set") | Suggests a bundle or related guide in the basket | Nothing — it just adds another item to the basket/another checkout link, same as any add-to-cart. |
| Cart with more than one item | | |

### Cart with more than one item

- If your provider supports a real multi-item cart (Payhip, Shopify): put
  one checkout link per **bundle**, and for loose multi-item baskets rely on
  the provider's own cart if it offers a "buy button" that adds to a
  provider-side cart. Simplest robust option: keep one `checkout.url` per
  product/bundle and let the site's own basket handle the *browsing*
  experience, while `provider: "links"` sends people to your provider
  correctly per item (see below) — full provider-side multi-item carts are
  a nice upgrade but not required to go live.
- With **exactly one item** in the on-site basket, the checkout button
  redirects straight to that item's `checkout.url`.
- With **more than one item**, the single checkout button is replaced with
  a *"Checkout this item"* button next to each line, plus a note explaining
  that the provider checks out one item at a time. This is the honest,
  no-invented-API way to handle providers (like plain Stripe Payment Links)
  that don't support a shared multi-item cart.

## Order confirmation & delivery

- Point every checkout's success URL at `/vaults/thanks/`. That page fires
  an analytics `purchase` event and links to "Your Library" and the
  catalogue. It does **not** know what was bought — the provider's own
  confirmation email is what actually delivers the files.
- Set up your provider to email the PDF/ePub as an attachment or permanent
  download link the moment payment clears — that email *is* the delivery
  mechanism the FAQ and Refunds page describe ("instant email with a
  permanent link").
- If you have a provider customer portal (Payhip does), paste its URL into
  `config.checkout.customer_portal_url` — "Your Library"
  (`/vaults/account/`) will then show a primary "Open your library" button
  instead of the "Resend my downloads" fallback form.
- Without a portal URL, "Your Library" shows a form (`data-subject="Resend
  downloads"`) that emails you directly via FormSubmit — resend the files
  by hand within one working day, as the copy promises.

## Refunds

The 30-day money-back guarantee is handled by **you**, by hand, per the
Refunds & Delivery page: the customer emails with their order reference,
you refund it in the provider's dashboard. There is nothing to configure
for this — it is a policy, not a feature.

## Regenerating the store

Everything under `vaults/` (the door, the five category pages, all 18
product/bundle pages, the basket, account and thanks pages) is generated —
never hand-edit files inside `vaults/`. Change `data/products.json` (new
product, price, coupon, bundle, checkout link, `config.status`) or the
templates in `tools/templates/`, then run:

```
python3 tools/build.py --store --only vaults
```

This regenerates the store and then re-injects the shared nav/head/footer
partials into every page under `vaults/`. Run it again to confirm it is
idempotent (it prints "updated" for every generated page every time,
because `store_build.py` always rewrites the page fresh before the partial
pass runs — that is expected; the important thing is the resulting bytes
are identical run to run).
